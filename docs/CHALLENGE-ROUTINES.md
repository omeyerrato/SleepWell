# Ordered wake-up routines

Board 04's routine screen is now an ordered configuration, not a one-type selector. Numbered cream rows show each task and its actual round/shake count. A chevron opens that task's configuration; its separate options control moves it up/down or removes it. Available-task plus controls open the new task configuration, and Use confirms that local step. Save routine applies the ordered draft to the alarm editor; only Save alarm writes the alarm/scheduling boundary. Back cancels unfinished task/routine edits. Draft order, current settings and an open picker survive activity recreation.

Supported existing task engines: Math addition, symbol-pair Memory, digit Sequence, Retype, accelerometer Shake and enrolled NFC tag. Math/Memory/Sequence/Retype each require their configured 1–6 rounds. Shake requires 5–30 deliberate shakes as one task; NFC requires one matching enrolled tag. Routines contain 1–8 tasks. Reorder uses an explicit options menu, not a fake nonworking drag handle. No preview button is shown because a full inert interactive preview is not implemented. QR scanning, walking/steps, per-location NFC enrollment, configurable math complexity and per-task challenge templates remain missing.

Alarm JSON adds an optional routine array. Existing JSON without it retains its scalar challenge/difficulty semantics: repeated answer tasks still require every old round, Shake keeps its old difficulty-times-five target, and NFC still requires one enrolled tag. Scalar fields mirror the first new step for older consumers. An unsupported/malformed array is preserved on read/write and marked invalid; the editor requires an explicit valid replacement, backup validation rejects it, and runtime uses the existing scalar fallback instead of dropping required tasks silently. No database schema or existing alarm row migration is needed.

AlarmActivity chooses its current type and local round from the saved occurrence's total completed count. Completing Shake or NFC advances through the same cursor as math; neither bypasses the remaining routine. Each answer/NFC callback captures its occurrence and current unit so a delayed or duplicate completion cannot skip a later unit or a new alarm. Active sensor samples are ignored across task boundaries and while paused. Per-occurrence shake counts survive recreation; manual answer-task state remains until that round succeeds. Existing snooze, backup, wake-up check and debug-only developer-stop behavior remains.

The current stack is Java Views, existing explicit factories/ports, JUnit4 pure tests and AndroidX UI Automator in guarded CI-only instrumentation. No framework migration is needed for this flow. Ten domain tests exercise scalar migration, mixed progression, physical-task continuation, stale-unit callbacks, restored position, immutable order/configuration and bounds. The new ChallengeRoutineFlowTest uses a private SQLite database and fake scheduling port, forbids launching AlarmActivity, and verifies real rows/pickers, reorder/remove, Cancel, recreate, Save/reopen, JSON round-trip, malformed backup rejection and original preferences/other-alarm preservation. It starts no service or physical output. Existing AlarmMenusFlowTest retains its picker cancel/state/snooze/save assertions while expecting addition of Memory to the routine rather than replacement of Math.

Expected new CI captures: routine-legacy, routine-ordered, routine-reordered, routine-recreated, routine-removed, routine-reopened (six). Native execution and original screenshot comparison are pending. Pure tests/builds cannot verify live hardware task recognition or mark the alarm flow visually complete; no alarm will be run on the user's phone for this work.
