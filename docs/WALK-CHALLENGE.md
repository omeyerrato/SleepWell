# Walk challenge: Android steps, not shake detection

The routine can add Walk as one task with a per-task target of 5–100 steps. Its configuration uses the existing owned cream/Inter step-target picker, explicit Physical activity access state and a user-invoked permission/settings control. Permission requests never run from the ringing activity or from saving an alarm. A missing sensor, denied/revoked permission, or listener registration failure displays a math fallback for that one task; solving the fallback still leaves subsequent routine tasks required. The routine's existing occurrence/unit fences and completion semantics remain intact.

The platform adapter prefers TYPE_STEP_DETECTOR, falling back to TYPE_STEP_COUNTER. It never registers the accelerometer, measures shake magnitude or treats shake events as walked steps. Android's step events are estimates and can be late or mistaken; this is not a guarantee that a person has crossed a particular distance. Detector values must equal one, and timestamps must be distinct and at or after activation. Counter readings must be finite whole nonnegative totals. The first fresh counter sample establishes a baseline, rather than awarding boot-total steps. A decreasing counter establishes a new baseline without awarding steps. Listener ownership ends when the alarm activity pauses or changes task.

Only earned steps are restored for the same alarm occurrence and task unit. Every resume starts a fresh registration and counter baseline, so steps taken while paused or before activation are not awarded. This conservative counter fallback can discard the first observed step, and Android can delay counter reports by up to ten seconds. No continuous background step history or health record is created. The pure owner fences late callbacks by listener generation, occurrence and task unit, clamps progress to the target, and delivers a task's completion once.

New routine JSON includes an integer steps field for Walk and requires one round. Counts outside 5–100, strings/fractions and missing targets are invalid. Older valid routines keep their JSON and behavior. Scalar legacy alarms with an old unknown Walk string keep their previous Math fallback; a genuine Walk task is explicitly represented by the new routine array. No schema migration changes stored user records.

Primary Android documentation: [motion sensors](https://developer.android.com/develop/sensors-and-location/sensors/sensors_motion) describes the two step APIs and counter latency; the [Sensor reference](https://developer.android.com/reference/android/hardware/Sensor) specifies cumulative counter resets and detector values; [runtime permissions](https://developer.android.com/training/permissions/requesting) requires contextual consent, current grant checks and graceful denial handling. ACTIVITY_RECOGNITION is the only new permission; optional step-sensor features do not exclude other phones. Permission denial/permanent denial has a visible alternative and never loops automatically.

Nine WalkSessionTest cases use injected step ports/effects to exercise detector validity, cumulative baselines, paused/old-boot exclusion, duplicate/stale generations and occurrences, unavailable/denied/registration errors, restored progress, exactly-once completion and routine continuation. Existing routine tests continue to run. WalkConfigurationFlowTest is emulator-CI-only, uses a private alarm database, a fake permission action, and a step-port factory that throws if constructed. It exercises the real target picker, needed/granted/settings/error/unsupported states, draft recreation, Save/reopen, strict target JSON, and unchanged original preferences/other alarms. No AlarmActivity, permission dialog, sensor listener, service or physical output runs in the native configuration test.

Expected six PNGs: walk-permission, walk-ready, walk-settings, walk-error, walk-unavailable, walk-reopened. Actual native execution and strict visual comparison remain pending; no phone alarm or step-recognition test will be run for this feature. The task currently uses the existing exercise glyph pending the parent's pinned footprints asset. QR/location enrollment and an interactive silent routine preview remain separate missing features.

The follow-up also contains sensor discovery and unregister exceptions: discovery failure shows the same per-task math fallback; release failure invalidates the callback owner and prevents rearming it. An additional injected release-failure test verifies no crash, stale progress or completion. This does not substitute for a later permitted real hardware assessment.
