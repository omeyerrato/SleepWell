# Optional sunrise alarm time (F103)

This is a **time basis**, separate from the existing screen sunrise / flashlight / bedroom-lamp outputs. In an alarm’s editor, **Time basis → Sunrise time** accepts manual latitude and longitude, an offset from −120 to +120 minutes, and explicit consent to use the selected ordinary clock time when sunrise is unavailable. The next computed date/time and fallback reason can be reviewed before returning to the draft. Only **Save alarm** persists and reconciles scheduling. Cancel, recreation, disabled state and the existing exact-alarm-access/error flow remain intact.

No location permission, geocoder, network lookup, provider account, background location or automatic coordinate default is introduced. Coordinates stay at the user’s explicitly selected location until edited. The phone’s current time zone owns target dates, weekdays, explicit alarm dates and calendar rules; the existing time-zone-change receiver recomputes deadlines. Update coordinates when travelling. Choosing Clock time explicitly removes the optional time basis. Reusable alarm defaults transfer behavior, never this location or time basis.

## Calculation and fallback

`SunriseMath` is an original Java implementation of the published NOAA fractional-year equation-of-time, declination and hour-angle equations, with the conventional 90.833° apparent sea-level horizon. It iterates UTC sunrise estimates and selects the UTC event belonging to the requested date in the explicit zone. UTC candidates on both adjacent dates handle the date line. Results are rounded to a minute. No third-party solar library or copied implementation is included.

Supported calculation years are 2000–2100. A polar day/night, unavailable crossing, unsupported year or offset crossing the chosen local date uses the user-acknowledged ordinary fallback time in the same current phone zone. Fallback follows the existing Java local-time DST gap/fold policy. A dated alarm remains one date; recurring weekdays use the actual calculated daily instant. A completely missing historical local calendar date is skipped for repeating alarms rather than creating a duplicate fallback. This is an approximate astronomical estimate, not a prediction of first visible sunlight: terrain, elevation, weather and atmospheric refraction can shift observed sunrise. Near polar transitions, fallback can occur even if a higher-precision model predicts a brief crossing. No unbounded accuracy claim is made.

## Scheduling and compatibility

Absent `solar` metadata retains legacy JSON, clock scheduling and schedule keys exactly. A present optional strict v1 object stores finite coordinates, bounded offset and acknowledged fallback; malformed or unknown metadata is retained for explicit repair and cannot schedule or pass backup validation. There is no SQLite migration. Portable backups retain manual coordinates and time basis, but the existing restore flow disables all alarms and clears pending skip ownership before any scheduling.

The current schedule signature includes the exact canonical solar configuration. Old queued deadlines, stale editors and skips cannot become authority for a changed location/offset. Existing exact-alarm admission, last-consumed deadline, smart-wake window, explicit date and calendar receipt checks remain in force. UI time summaries show the computed next time, and Tonight’s planned window uses that projected wake time rather than the fallback clock.

Ordinary clock skips remain their original seven-field v1 encoding. Solar-only v2 skips add a frozen absolute **computed solar base**, its exact configuration signature and target date in the stored creation zone. Strict decoding rechecks that calculation and rejects mixed clock/solar skips or a changed deadline. Calendar rules may advance the delivered time: the existing calendar receipt owns that adjusted deadline separately, and skip/undo expiry uses the actual adjusted time. The frozen base prevents an early calendar adjustment from accidentally skipping the next day’s sunrise. No second ordinary fallback alarm is scheduled alongside sunrise.

- `SunriseScheduleTest`: 9 pure methods for actual offset/weekday/date instants, single-date exhaustion, polar/unsupported-year/DST fallback, cross-date offset fallback, frozen one-occurrence skips, changed phone zone, finite/consent bounds and a historically missing calendar date.
- `SunriseAlarmTest`: 4 pure methods for actual `Alarm.next` and delivery-window/claimed fences, dated/polar single delivery, malformed configuration and schedule ownership, plus exact absent-field legacy behavior.

Covers portable/default compatibility, malformed import rejection without replacement, save/skip/undo/restore/reopen, stale coordinate edits, forged v2 deadlines/mixed types, and a calendar-advanced solar skip whose expiry owns its actual delivered time.
