# Smart-window automatic start uses the projected alarm deadline

The explicit Automatic tracking → Before smart window → Arm tonight flow now derives its lead-in from the same `AlarmSkips.next` projected deadline used by current alarm routing. The platform passes one captured wall time and time zone into the helper: raw occurrence comes from `Alarm.next(max(now,lastOccurrence),zone)`, then `CalendarAlarms.preview` retains eligible installed calendar receipts or applies the current calendar plan.

This replaces the old hour/minute-only `SleepMath.nextOccurrence` path, which incorrectly treated dated, solar and skipped alarms as ordinary repeated clock values. It preserves the real selected local date, sunrise calculation/acknowledged fallback, skipped occurrence, calendar holiday/meeting adjustment, DST resolution and already-consumed occurrence fence. Relative naps and malformed nap/date/solar/skip metadata are excluded from this ordinary-alarm arm mode.

The lead-in remains 45 minutes before the selected alarm’s smart-window start (`projected deadline − (smartWindow+45) min`). An already-open lead-in can start now only if its actual deadline is still future. Zero, expired and past projected deadlines never admit tracking. An empty eligible set shows the existing prerequisite error; four-hour waiting bounds, explicit visible foreground/microphone admission, notification access, cancelled/expired waits and all real recording/output behavior are unchanged. Saving settings does not arm or start anything.
