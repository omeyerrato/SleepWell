# Privacy history cleanup

The existing Privacy deletion row delegates to `HistoryEraseUi`. Confirmation starts one background `HistoryErase` task with the application context and the `Records.Factory` captured before submission. The worker opens and closes its own Store; it never uses an Activity-owned database or changes preferences, alarm schedules, or services. `SoundClips.eraseHistory` commits the schema-6 deletion journal and record removal before attempting private audio unlinks.

`HistoryEraseJobs` retains busy, completed, pending-file, and error results for the process lifetime, keyed by storage-factory identity. Recreating the Activity reattaches to the same operation; another confirmation cannot enqueue duplicate deletion while busy. Detached bindings stop observing and release their dialog. The worker retains no Activity. Active tracking blocks history deletion.

Pending audio is described explicitly. The row becomes **Retry audio cleanup** and calls `SoundClips.recover`, which does not delete new history created after the earlier erase. Every new Privacy binding, including rows already attached when built, refreshes persisted pending counts in the background and offers the same retry. Reinspection retains earlier action errors while refreshing those counts; transient inspection errors clear after a successful read. Process death can interrupt work; this is not a persistent OS job. The committed journal preserves outstanding file cleanup across that interruption. The UI does not claim those bytes were removed until pending rows clear.

Nine pure `HistoryEraseJobsTest` tests cover duplicate submission, retained completion, error/rejected-executor states, separate storage identities and safe teardown. `PrivacyHistoryFlowTest` is a guarded CI-only native test using real isolated SQLite and owned private file fixtures. It exercises the actual Privacy row and confirmation/cancel, background busy and injected storage-error states across recreation, pinned factory, real nonempty-directory unlink failure, pending state after recreation, a cleanup retry that preserves a newly added record, and a new journal entry discovered when reentering Privacy from Settings. It checks fixture alarms, global preferences, the original database backup and original private-file hashes. Expected native captures are `privacy-history-ready`, `privacy-history-busy`, `privacy-history-error`, `privacy-history-pending`, and `privacy-history-done`. It never records, plays audio, schedules alarms, or tests physical outputs.
