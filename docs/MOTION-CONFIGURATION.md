# Motion sensor configuration and engine wiring

The selected Phone movement row in Tracking setup now opens `MotionSensorActivity` and shows its saved sensitivity when the user returns. Contactless sonar remains explicitly unavailable; this work does not simulate sonar, emit sound, or claim calibration. Boards 06-left and 10-middle guide the dark setup and cream configuration layouts. The current Phosphor phone illustration remains simpler than the reference's rendered phone artwork; final screen fidelity is pending actual Android capture review.

Motion configuration registers the accelerometer at a requested 200,000 microsecond interval (approximately 5 Hz) only while the Activity is resumed. Registration failure, missing hardware, unreliable accuracy, no samples and stale samples have explicit states. Listeners are unregistered on pause/destruction. A private, injectable `MotionPort` supplies callbacks. The preview and tracking engine share `MotionFilter`, preserving the existing .85/.15 gravity-removal filter. Preview bins contain actual half-second RMS samples from the last 15 seconds; missing bins stay blank, and the preview does not create a sleep record or save raw samples.

Low/Medium/High save only `motionSensitivity` after **Use this sensor**. Draft values survive recreation and are discarded on Back. Reads do not persist defaults. Saves use a pinned preference factory on the retained `PlanOperations` worker and report storage/concurrent-change errors. An unavailable or unregistered sensor cannot be selected by the save button.

`TrackingService` loads one immutable `MotionProfile` when a manual or armed run starts. Low, Medium and High multiply heuristic inputs by .5, 1 and 2 respectively. Medium preserves the prior smart-wake and stillness decisions. The gain changes activity accumulation/smart-wake eligibility and the existing automatic phone-stillness heuristic; sample-count, screen-use, maximum-wait and minimum-quiet-time gates remain enforced. Saved minute RMS readings, live raw readings and historical data are **not** multiplied or rewritten. Changes apply on the next recording/armed run, not halfway through the current one. These gains are app heuristics, not clinically calibrated mattress sensitivity or sleep-stage detection. Idle phone movement cannot establish that a person is asleep.

Primary references: [Android motion sensors](https://developer.android.com/develop/sensors-and-location/sensors/sensors_motion) describes accelerometer/gravity filtering; [Android sensor best practices](https://developer.android.com/develop/sensors-and-location/sensors/sensors_overview) covers foreground collection and unregistering listeners on pause. [Sleep as Android's tracking documentation](https://www.sleep.urbandroid.org/docs/sleep/sleep_tracking.html) explains mattress-dependent phone movement and separate sonar requirements. Those sources do not validate this app's Low/High gain values.

`MotionConfigurationTest` covers default-policy equivalence, actual sensitivity-dependent smart-wake and automatic-stillness changes, retained minimum durations/sample-count gates, invalid inputs, filter warmup/reset, stale/missing bins and identical preview/engine filtering. `MotionConfigurationFlowTest` is a guarded emulator-CI-only native flow. Its port is entirely replaced before Activity creation; no physical or emulator sensor listener is registered. It verifies injected live bins, the actual accessible slider, unsaved recreation, Save/reopen, concurrent-save conflict retained across recreation, engine-profile consumption, listener cleanup, hardware-unavailable and registration-error states, and unchanged global preferences. Expected captures: `motion-settings-ready`, `motion-settings-changed`, `motion-settings-recreated`, `motion-settings-reopened`, `motion-settings-conflict`, `motion-settings-unavailable`, `motion-settings-error`.

Compilation and model tests do not verify real overnight reliability, sensor quality, clinical accuracy, native screenshot fidelity or device behavior. Actual native test execution/capture comparison and controlled hardware evaluation remain separate gates. No phone, alarm, microphone, speaker, flashlight, lock or power tests were performed for this change.
