# QR/NFC enrollment interaction fixes

Baseline: `2aa537ce56fa048ad4bb9f0776e03f40b6eb1ac5`. Scope: enrollment callback ownership, permission continuation, cancellation and recreation. No task type, grant, saved code/tag format or alarm behavior is removed.

| Issue | Concrete source behavior | Bounded fix |
|---|---|---|
| NFC enrollment after Cancel/pause/replacement | MainActivity's reader callback posted an unconditional `Prefs.put("nfcTag", ...)` to the UI queue. Cancel only disabled reader mode; a previously queued callback could still overwrite the enrolled tag. Pause did not close the enrollment dialog/reader. | [NfcEnrollment](../app/src/main/java/org/sleepwell/app/NfcEnrollment.java) gives one visible dialog a reader generation. Cancel/dismiss, Main pause/destroy and replacement invalidate it before cleanup. A queued callback must still own that exact focused dialog and a live Activity, and NFC must remain enabled. Empty IDs are rejected. Only a current callback invokes the existing tag-save action. Reader start/cleanup failures no longer crash the enrollment UI. |
| QR canceled request revived by late permission result | `onRequestPermissionsResult` always set `wantScan=true` when access was READY. Moving to Fallback had canceled scanning, but a late result could restore that flag; Back followed by recreation could then start a camera that the user had canceled. Finishing enrollment was not checked by `current()`. | [QrCodeActivity](../app/src/main/java/org/sleepwell/app/QrCodeActivity.java) requires an outstanding owned scan intent, enrollment mode, code route and non-finishing Activity before continuing the permission result. Fallback, format changes, generation, Save and Back invalidate the pending request. Current/scan-button gates reject finishing or destroyed Activities and duplicate pending requests. Runtime-prompt and Settings-return action metadata survive recreation; no permission grant is cached. |
| Stale permission controls after Settings/revocation | Resume only rebuilt the QR screen when `wantScan` was true, leaving the displayed access action stale when the user had already captured a code or canceled scanning. | Resume refreshes the native controls from the current permission state while preserving label/hash/format/fallback draft. Settings return can continue only the still-owned explicit scan request; returning without access cancels that continuation. |
| Failed camera prompt recorded as a completed request attempt | QrCameraAccess set `qrCameraAsked=true` before invoking Android. A launch exception left that marker set, so a first attempt could incorrectly become a Settings-only state without showing a prompt. | [QrCameraAccess.request](../app/src/main/java/org/sleepwell/app/QrCameraAccess.java) restores the prior asked-marker value if requestPermissions throws. It does not change any permission grant. This platform exception branch is source-reviewed, not runtime-exercised. |

NFC keeps the original reader technologies (A/B/F/V and skip-NDEF), hexadecimal identifier and `nfcTag` preference. It remains a wake-up habit check, not a cryptographic credential. Cancellation/recreation retains the previously saved tag and requires a new explicit setup action. MainActivity integration is limited to NFC setup plus pause/destroy cleanup.

QR/barcode formats, captured hash, location label, fallback task and final Save boundaries remain intact. The ringing challenge still cannot request camera permission, and its occurrence/unit/code identity checks are retained. [QrCameraAccess](../app/src/main/java/org/sleepwell/app/QrCameraAccess.java) still routes permanent denial to Android Settings. Camera cleanup/generation checks in QrScanSession and QrCamera remain unchanged.

The associated exported-input boundary was reviewed: QR enrollment and printable-code Activities are private in the manifest. MainActivity accepts finite page/group navigation and display metadata; incoming extras do not supply an NFC tag, create a QR enrollment result or enable reader mode. Enrollment still requires the visible setup action. Generated QR results remain request-correlated and reject data URI/ClipData/selector; generated export and code/alarm Save stay separate. No additional exported input bypass was established in this pass.

The existing single method in [QrCodeConfigurationTest](../app/src/androidTest/java/org/sleepwell/app/QrCodeConfigurationTest.java) now adds two bounded regressions without adding a test-method batch:

- A fake NFC reader delivers a queued tag, then the dialog closes before delivery; the old target remains. An old reader cannot write into a replacement dialog; the current reader can complete. This uses an atomic fixture value, not actual app tag preferences or hardware.
- A fake camera permission result arrives after entering Fallback; Back/recreation must not create a camera until the user taps Scan code again. Existing private-store, stale-camera, draft, fallback, strict-restore and task persistence checks remain.

Verification: `:app:compileDebugJavaWithJavac :app:compileDebugAndroidTestJavaWithJavac --offline --console=plain` passed, including a final 6-second incremental confirmation after the permission-launch rollback change. Source links and `git diff --check` passed.

These focused native regressions are **not executed** in this change. No CI, emulator/phone, camera, NFC radio, alarm, audio, haptics, flashlight or export/print operation was run. Broad interaction/security acceptance remains open; compilation, source inspection and fake-callback fixture code do not establish physical NFC/camera behavior or whole-app security.
