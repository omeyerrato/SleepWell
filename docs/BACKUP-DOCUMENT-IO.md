# Backup documents: responsiveness and ownership

ANR risk: yes (HIGH) in the original document path at `f2af038`. This is a static source finding, not an observed ANR or a measured timeout.

## Source audit

The reviewed scope is Main's backup-document callback and destructive restore action. The Android Activity lifecycle/input dispatcher executes `onActivityResult` and button listeners on the main thread. In original `MainActivity.java:199–212`, JSON/CSV export called `Store.backup`/`Records.csv`, serialized the result, opened a document provider, wrote and closed its stream inline. Import opened/read/closed a provider stream, parsed and validated up to 8 MiB inline. These calls synchronously execute provider IPC, disk/database access or CPU loops without a worker dispatch. They can stall the lifecycle/input thread: HIGH, owned by Main's callback.

The original confirmation's positive listener called `Backup.restore` inline. That method validates and replaces SQLite rows transactionally, cancels platform schedules and deletes old private files before returning. Its verified call chain is Main's main-thread click listener → Backup.restore → restoreData / SQLite / schedule and file operations. It is another HIGH static risk; moving only the provider read would leave it intact.

Dismissed within this scope: selecting a request code and copying a URI string are bounded in-memory operations; no ANR risk established. No off-main mutation of an attached View was found in the old document path. The new worker has no Activity, Dialog, View or adapter reference, and publishes immutable state through the main dispatcher; background attached-View mutation is therefore not introduced. Other existing main-thread database/media paths are outside this audit and are not certified safe.

Primary Android guidance: [ANR diagnosis and blocking I/O](https://developer.android.com/topic/performance/anrs/diagnose-and-fix-anrs), [Activity threading](https://developer.android.com/reference/android/app/Activity#Threading), [ContentResolver document descriptors](https://developer.android.com/reference/android/content/ContentResolver#openFileDescriptor(android.net.Uri,java.lang.String,android.os.CancellationSignal)), [SQLite transactions and WAL](https://developer.android.com/reference/android/database/sqlite/SQLiteDatabase#beginTransactionNonExclusive()). The installed `anr-audit-and-fix/SKILL.md` and complete `references/risk_analysis_guide.md` were read and applied.

## Native flow

Board 12's cream, Inter typography, rounded controls and brown primary action are retained. Data & privacy's real JSON/CSV/import controls open a private Backup activity. It shows document selection, reading/writing progress, reviewed contents, explicit replacement confirmation, completion, cancellation and errors. A completed import is only a review: no database mutation occurs without the owned confirmation. Confirmation is tied to the exact retained review object. Duplicate confirmations cannot queue another replacement.

The single retained job is keyed by the exact `Records.Factory` identity captured on entry. Its worker opens/closes its own Store using application context. Main's lifecycle-owned Store is never handed off. Rotation and same-process reopen observe the same job and result. No worker closes a provider/database, waits, joins or accesses a View from Activity teardown. The Activity's main-thread observer only renders immutable state. Ordinary Back remains on progress during the non-cancellable replacement phase, avoiding the normal route back into Main's synchronous DB rendering mid-transaction.

No 8 MiB document or JSON object is put into a Bundle. If a saved Activity returns in a new process, it shows an interrupted/needs-review state rather than repeating replacement. A cold new task without saved state has no retained result: the user must choose/review the file again. The app does not claim durable WorkManager execution or process-death completion.

## Bounded document access

Provider open/read/write/flush/close, UTF-8 conversion, JSON parsing/validation and SQLite work run on the worker. Input and both JSON/CSV outputs are capped at 8 MiB of bytes, not characters. UTF-8 decoding rejects malformed input; imports reject nesting deeper than 64 before JSON parsing. A broken stream repeatedly returning zero cannot spin forever. Output is prepared and size-checked before the destination is opened/truncated. CSV preserves the existing columns, edits, notes/tags and unfinished-record representation. JSON preserves portable format 4, including original sound estimates, corrected user labels, favorites and explicit interrupted-tail scope. No audio bytes, clip paths or app settings are exported.

Cancellation invalidates the generation immediately. Native provider cancellation/descriptor close is submitted to a separate bounded worker, since either may block in a provider. Late reads cannot create a review or authorize replacement. An outstanding operation retains its worker slot until it actually exits, preventing overlapping provider jobs. Cancellation is best effort when a provider ignores cancellation or blocks forever; the UI remains responsive but the storage scope cannot start another document operation until that access returns. A cancelled/failed export can leave a partial provider document; no rollback/delete of the user's chosen destination is promised. The system picker is used in production; tests replace its boundary and provider transport, so native fixtures do not certify a particular storage app or DocumentsUI.

## Replacement fencing and cleanup

The reviewed local identity hashes ordered, typed values from all affected tables: alarms, sessions, epochs, pauses, edits, creation-request tokens, sound events (including labels/favorites), clips and pending clip deletions. Cursor integers stay exact; identity is not derived through lossy JSON doubles or the portable subset. The digest is recomputed under the actual replacement write transaction before mutation. Any changed local data rejects the old review. No schema/version change is involved.

Runtime idle is checked before preparation, after reading/identity capture, before replacement, during inserted rows and immediately before commit. Existing TrackingService.running and AlarmService.active are volatile. Tracking sets running before its first Store access. Alarm admission requires an earlier fence: Scheduler.fire may wait for database work before it sets the ringing preference. Genuine starts, effect-eligible private alarm/nap receiver attempts and wake-check ownership reads therefore increment a nonblocking process-local admission counter before their first Store access; stale/no-op recurring requests must be rejected before the tracking notification. Malformed/non-effect receiver inputs do not notify. A well-formed but stale private delivery or current wake-check ownership query can conservatively invalidate a review rather than wait on replacement. Counter saturation fails closed. The worker never holds Scheduler.class across document or replacement work. Schedule retirement rechecks admission before each operation and skips a later enabled alarm. Legacy platform cancellation identities are not a cross-process transaction: a tiny check-to-cancel race and interruption after commit remain limitations, never a guaranteed-delivery claim.

A new admission between insertion checkpoints aborts/rolls back replacement, including its staged audio-deletion journal. A waiting new writer can then insert its record into the preserved database. There remains a small final-check-to-SQLite-commit interval; the code does not promise global exclusion of runtime admission. SQLite serializes writes admitted after the final check until the replacement commits, so that later recording's new row is inserted afterward rather than being deleted by the completed transaction. No recording/service is started by a test to establish this; a deterministic injected admission and private waiting DB writer exercise the boundary.

Existing formats 1–3 and format 4 retain their validation/restoration semantics. Imported alarms stay disabled; imported relative naps retain metadata but become inactive/cancelled. Restored sound metadata remains analysis-only (`clip=NULL`). Old clip deletion intent is staged in the same transaction as row replacement. Actual unlink recovery occurs only after commit, against the pinned database and private path contract. Cleanup failures/pending files, pending-count failure and Store.close failure after commit are reported as a committed restore needing cleanup, rather than claiming nothing was restored or that all bytes disappeared. Schedule retirement is post-commit and injectable; an alarm enabled by a later editor is not blindly cancelled. This is not a durable cross-system transaction: a process crash after DB commit can precede platform schedule retirement. Existing disabled/restored ownership checks still govern eventual receiver delivery; review alarms after restore.

## Database contention limit

Database mode is deliberately unchanged. A private native regression compares explicit rollback-journal exclusive reader contention with raw WAL snapshot reads; it is not an executed measurement until its CI result exists. Existing Records snapshots also use non-exclusive **write** transactions, so switching one helper to WAL alone would not establish app-wide responsiveness. Independent Store helpers and all other callers need a separate coordinated audit before changing a global journal policy. This change removes the proved direct document/restore work from the UI callback; it does not claim every other screen's synchronous query/write is safe during competing database work.
