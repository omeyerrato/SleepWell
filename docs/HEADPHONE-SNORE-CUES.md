# Headphone sound constraint for snoring cues

The opt-in Sound output setting constrains **sound only**. It defaults off, so existing ToneGenerator/media-route behavior and saved cue options remain unchanged. Vibration-only mode is unaffected. In Both mode, vibration still follows the selected intensity/repeats even when sound is skipped. Changing sound routing does not enable snoring analysis or snoring cues. It changes the next cue's output settings, with the existing two-minute cooldown and30cue budget unchanged. Preview still requires a live visible token, uses one low-intensity pulse, has a separate shared preview budget, and never starts the microphone.

Open Snoring cues → options → Sound output. The supporting screen distinguishes connected endpoint availability from verified output routing. It offers an explicit draft, Save, recreation and Back-discard behavior. Device addition/removal callbacks update availability only; opening the screen does not create an audio output. A previous skipped/failed sound is shown separately. The main board07 cue layout stays compact.

## Supported routes and actual behavior

Wired headphones/headsets, USB headsets and API31+ BLE headsets are accepted. Ordinary Bluetooth A2DP may mean a speaker; Bluetooth SCO/call routes, generic USB audio, hearing aids, broadcasts, unknown routes and speakers are not accepted. The unsupported Bluetooth-media case is visible in settings. No Bluetooth permission, pairing, communication-device switch, global media volume change, network or dependency is added. Device names/addresses are not collected.

The headphone sound adapter requests a preferred endpoint on its own AudioTrack, starts with muted silent PCM, then checks the actual route while that track is playing. It does not treat setPreferredDevice success or an attached device as proof. API36 checks the full routed-device list; earlier supported APIs check the single routed device. Exactly one supported endpoint matching the chosen ID must be reported. Audio is queued in at most20ms chunks, with a route check before making the track audible, immediately before enqueueing and after enqueueing. A routing callback or periodic check that loses the route mutes, pauses, flushes and releases the owned track; it never falls back intentionally to the phone speaker. Nonblocking short/zero writes are handled without inventing transferred frames, with bounded setup/drain deadlines. The track is allowed to drain the actual queued frames before the final release. Closing/disabled/ringing tokens suppress pending work. Night output is owned by the tracking recorder and does not require an Activity; preview remains Activity-bound.

These are public Android routing checks, **not a guarantee of zero speaker leakage**. The OS may reroute queued samples before its callback arrives; OEM routing reports, duplicated hardware output and accessory type misreporting are outside this app's control. API30–35 cannot inspect a multi-route list. BLE support/type reporting and audio latency vary by device. Wired/USB/BLE hardware output, route-loss latency and actual vibration remain unverified; no physical audio output was tested. A2DP headphone support is deliberately incomplete until there is an explicit trustworthy way to identify the user's device instead of assuming every Bluetooth media sink is headphones.

## Public API evidence

- [AudioRouting](https://developer.android.com/reference/android/media/AudioRouting): preferred devices need not be actual routes; actual route queries are valid while playing; API36 adds the full routed list.
- [AudioTrack](https://developer.android.com/reference/android/media/AudioTrack): public routing listeners, stream writes, nonblocking/short-transfer contract, playback-head position, mute/pause/flush and release.
- [AudioDeviceInfo](https://developer.android.com/reference/android/media/AudioDeviceInfo): explicit wired/USB headset types, BLE headset added31, and generic A2DP type.
