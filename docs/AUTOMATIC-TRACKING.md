# Automatic start: foreground-armed candidate

This is an opt-in, **one-night foreground wait**, not unattended sleep recognition.
Open Tracking setup → Choose automatic start, select a radio option, then Arm tonight.
Saving a preference alone does not start sensors or schedule background work.

Implemented source paths:

- At bedtime: the saved local bedtime, including its calendar time zone, anchors an elapsed-realtime deadline.
- Before smart window: 45 minutes before an enabled alarm's smart window. A missing enabled smart alarm is an error.
- After settling down: at least 15 minutes of low accelerometer movement while the screen is off. Five-Hz sampling is requested; a gap over two seconds, insufficient event coverage, screen use, invalid energy, or movement resets evidence. A timer alone cannot trigger this mode.
- The wait expires after four hours. Schedule modes must be armed within that period. An ongoing silent notification provides cancel/open controls.
- No session row is created while waiting. A qualifying trigger creates a normal recording at the actual start time; pause/resume/end use the existing tracked-session path.
- Movement-only automatic recordings are the default, regardless of the manual microphone/clip preferences. Record sounds and Keep sound clips are separate opt-ins for automatic runs. Microphone permission is requested while the settings Activity is visible, before arming. A requested microphone foreground type must be established successfully at that initial foreground start. No audio recorder is created during the wait; it is deferred until the recording transition. Failed establishment cannot be retried from the background, and permission revocation disables audio for that armed run. Movement recording can continue when audio becomes unavailable. Clips use an immutable per-run opt-in rather than inheriting the manual save-clips preference.
- Sleep audio stays off for all automatic runs. No boot receiver starts this flow, and it does not silently upgrade into a microphone foreground service from the background.
- A stopped/killed wait is never represented as still active merely because its saved preference remains. Reopen and arm again; the service is deliberately `START_NOT_STICKY`.

Limitations: phone stillness does not prove a person is sleeping; an idle phone on a table can qualify. No Google Sleep API, activity-recognition model, automatic wake detection, retroactive missed-night estimate, sonar, charging policy, or all-day background inference is implemented here. Continuous foreground motion sampling uses a partial wake lock while armed and can consume battery. Device/process interruption can end the wait. Schedule changes after arming apply the following time it is armed. The elapsed deadline survives wall-clock changes within a live service, but the service does not resume a wait after a process kill or reboot.

Evidence is deliberately scoped. `AutomaticSleepTest` and `AutomaticStartTest` exercise production decision logic with sampled motion and clock inputs. `AutomaticTransitionTest` exercises the same recording-effect boundary used by the service, including exactly-once start, cancellation after qualifying evidence, screen/movement/signal changes before committing the start, expiry, and failed storage. `AutomaticCaptureTest` exercises default-off consent, initial foreground establishment, deferred capture, pause/close, permission loss, and independent clip consent. `AutomaticTrackingFlowTest` is an emulator-only native settings/storage flow with fake arm output; it captures `automatic-manual.png`, `automatic-stillness.png`, `automatic-sounds.png`, and `automatic-reopened.png`. That test cannot certify actual Android sensor delivery, screen-state callbacks, microphone foreground-service lifetime/deferred capture, or an overnight recorded-night transition. Those device effects remain unverified. No physical device, ADB, microphone, audio, alarm, vibration, flashlight, power, or screen-lock test is authorized for this milestone.

Reference behavior: [Sleep as Android automatic tracking](https://www.sleep.urbandroid.org/docs/sleep/automatic_sleep_tracking.html). Platform boundary: [Android foreground-service restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start). The supplied board `10-phone-sensors.png` informs the native radio rows; this candidate does not claim full board fidelity before Android screenshot comparison.

Android documents that microphone services require `RECORD_AUDIO` and cannot be created from the background; the microphone service type supports continuing microphone access in the background. The deferred-start contract here follows from establishing that service while the user arms it visibly; actual delayed microphone activation still needs platform lifecycle verification. See [microphone service type](https://developer.android.com/develop/background-work/services/fgs/service-types#microphone). Android can reject the initial start if visibility/permission requirements are not satisfied; that is reported as an error rather than silently retrying later.
