# Sound library: storage and review flow

Schema 6 supplies durable storage with board 07's inline recording controls, favorites, explicit deletion and retention settings. Explicit nightly ZIP export is in source; native/provider acceptance is pending. Existing estimates without saved PCM remain analysis-only rows. No physical audio or microphone tests were run, and real playback output is not verified by the fake-output UI tests.

## Additive schema 6

Migration 5→6 adds clips.favorite and sound_events.favorite, both default 0, an index for linked favorite events, and pending_clip_deletes. Existing alarms, session values, sensor readings, sound estimates and WAV files are preserved. Event favorites are independent: starring one estimate does not star every estimate in the same 10-second WAV. Retention preserves a WAV if its clip is starred or any linked estimate is starred. Removing expired audio nulls links through the existing trigger; the estimate and its star can remain as metadata.

SoundClips.favoriteEvent and favorite use identity checks before writes. Event identity includes session, original start, duration, category and model. Audio identity includes clip ID, session, original end timestamp and the private filename. Stale rows do not authorize deleting a replacement file.

A deletion intent is stored before filesystem changes. Failed unlink operations retain metadata and a pending row for an explicit retry; recover can finish after a process interruption. Shared legacy filenames remain until their last database reference is removed. Record/history/restore deletion stages audio identities transactionally before dropping rows. Recovery checks remaining path references and never treats a reused row ID as the original recording. FileSafety rejects paths outside the private clips directory.

## Parent integration required

- Replace MainActivity privacy's file-first deletion loop with a background call to SoundClips.eraseHistory(context,store). It first commits the data/journal transition, then recovers file deletions. Its boolean result is false if files remain pending, which the UI must report. Do not call FileSafety.deleteClip before staging.
- Remove TrackingService's old hardcoded 7-day pruneClips call/method. It would ignore favorites and run filesystem work on the service's main thread. NoiseRecorder now calls SoundClips.prune on its owned worker once per session when clip saving is enabled; the old service call must be removed at integration so it cannot bypass favorite retention.
- SoundClips.prune(context,store) reads audioRetentionDays (default 7, 0 means keep) and keepAudioFavorites (default true). SoundLibrarySettingsActivity now supplies owned choice controls and a Save & apply retention action: it persists the selected policy and prunes expired ended recordings on a worker, reporting pending deletions honestly.
- RecordEditor can continue deleting the returned paths: Records.delete now returns only files with no remaining clip references and stages recovery first. The next library open can call recover to complete journal cleanup.

## Real intervals and waveform data

RecordingSlice.contained computes an event's offset inside actual WAV duration and rejects partial coverage or overflowing times. ClipWave reads bounded PCM16 mono/stereo WAVs only, validates chunks/format, and extracts actual 64-bin peaks for the selected interval. Missing, empty, truncated or unsupported recordings fail rather than receive synthetic bars. There is no output playback in these classes.

SoundEventRows resolves chronological estimates and legacy recordings on a worker, clamps the visible interval to the edited night, and decodes only the first 50 matching rows (Load more is explicit). Legacy timing comes from actual WAV duration. Analysis-only or missing-file rows have no waveform or active Play control. Other/favorite filters and supporting settings are available from Sound event options; primary All/Snoring/Speech controls show actual counts. Deleting an estimate explicitly differs from deleting its shared WAV. The latter leaves linked estimates and favorites as metadata.

The inline view renders actual interval peaks, normalized relative to that recording's maximum for visibility; digital silence remains flat. The custom seek control has a 48dp hit area, keyboard navigation and Android range accessibility, with no inherited platform slider geometry. Two additional unmodified MIT Phosphor heart assets use the same pinned upstream commit as the existing family.

ClipReviewPlayer generation-fences preparation and state callbacks, requires an explicit foreground Play action, preserves position/filter/favorite state through recreation, and never resumes after focus loss. ClipPlayback owns MediaPlayer/file descriptors/focus on one worker. It revalidates clip/event identity and interval coverage before preparation, times out after eight seconds, coalesces seeks, bounds playback to the selected interval, and stops on pause, headset/noisy notification, completion or destruction. Tracking, a ringing alarm or active sleep sounds block review. It uses the existing media-stream volume, never changes global volume, never loops, and performs no network access. This native adapter has compiled but has not been exercised for real output.

## Explicit nightly ZIP export

Sound event options now opens Export recordings. The screen prepares an immutable ended-night snapshot on a worker, shows actual recording/event counts and audio size, and discloses that the ZIP contains complete raw clips, including audio outside edited sleep bounds. Only Choose save location launches Android ACTION_CREATE_DOCUMENT; cancellation performs no write. The app accepts only the returned content URI, uses no storage-wide permission, and makes no upload or network request. Android Files or another document picker/provider must be enabled. A selected cloud provider can require its own account/network. Provider behavior is not verified by fake-sink tests. [Official Android SAF contract](https://developer.android.com/training/data-storage/shared/documents-files).

NightAudioArchive supports at most60 WAVs,3600 estimates and64MiB of audio per night. It validates every private filename/row identity, complete PCM WAV structure/duration and record/event snapshot before writing. Generated recordings/001.wav-style entry names omit private source paths. The final manifest.json contains exact SHA256/lengths, actual raw/edited timing, favorites and uncalibrated estimate metadata; analysis-only rows reference no recording. The manifest is written after all recordings copy and the snapshot is rechecked. Consumers must still require a valid ZIP and verify every listed hash; a destination can fail even after manifest bytes have been emitted. Destination failure never deletes or mutates originals. A partial destination can remain after failure or process termination; retry explicitly through Android Files. This is an audio archive, not an importable SleepWell configuration backup.

SoundArchiveJob retains busy/result state and a pinned application-only worker through Activity recreation; no automatic retry/export occurs after recreation. Duplicate or late document results cannot reset an active export or enqueue another write. Closing rejects late callbacks and cooperatively interrupts private file work; provider cancellation/file-descriptor closure are requested off the UI thread. A provider can still block or ignore cancellation, so this is not a guaranteed provider timeout. A process restart during the system picker or export requires reopening/retrying, and cannot promise a completed document. NightAudioArchiveTest has3 native methods: exact ZIP/WAV/hash/metadata round-trip, stale identity/truncated WAV rejection before output, and empty/destination-failure source preservation. SoundArchiveUiTest has1 CI-only method with a fake Android document result and fake sink: library navigation, cancel/no-write, actual ZIP generation, retained success/no-repeat, and provider-failure UI. Four PNGs and a synthetic ZIP are requested; export native execution and screenshot comparisons remain pending CI. Real document-provider export has not been exercised.

Export preparation pins a SHA256 digest from the same descriptor used to validate each WAV, so an equal-size/equal-duration replacement is rejected. Before opening the chosen document destination, a maximum64MiB immutable snapshot is copied into a UUID-owned directory below the private cache. Source identity, favorite/event metadata and expected hashes are rechecked while holding the same lock as audio deletion. The database and deletion lock are released before provider access; deleting originals afterward cannot change the authorized snapshot. At most one snapshot/export can be active, including a blocked provider. Snapshot cleanup runs on success/failure/cancellation; the next export removes stale identity-owned directories left by process termination, without touching unrelated directories or a live snapshot. No cache FileProvider exists. If cache cleanup fails, later exports cannot silently accumulate additional snapshots. A source change aborts before destination access; failure after provider access can leave a partial destination. The final manifest describes the frozen snapshot, not a later live database query. Consumers still need a valid complete ZIP and matching hashes: manifest presence alone never proves success.
