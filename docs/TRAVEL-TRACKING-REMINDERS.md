# Silent reminders during manual recording

Travel mode's **During sleep tracking** switch is independent of flashlight arming and destination-time daylight reminders. It defaults off. Changing it edits the current trip draft; Save travel settings validates a reviewed, enabled, future light-cue window and notification permission before persisting it. The Light source child exposes Tracking reminder settings, the next saved time, delivery notice and separate Review & arm action. Changing zones, trip dates or cue windows requires the same explicit Save/review path. Disabling light cues while this reminder remains on produces a prerequisite error rather than silently enabling or removing anything.

Each saved home-zone cue-window start can produce one silent notification while the same manual recording is actively recording. The production gate reuses TrackingService.travelManual: ACTIVE/running, current nonempty manual token, no batch, automatic or recurring run, and an ACTIVE sonar state when applicable. Paused, pausing, stopped, absent and automatic sessions cannot qualify. The notification opens Travel; it does not arm pulses, start recording, play audio, vibrate or invoke the flashlight port.

A separate immutable private PendingIntent identifies trip revision, cue revision, start and end. Its receiver verifies the explicit action and identifier. Delivery durably consumes that identity before output, then rechecks current revisions, enabled preference, exact window, notification permission, recording session/token and lifecycle generation on the main thread. Pause and stop invalidate pending publication and dismiss a notification owned by this process. Duplicate, stale and clock-rollback delivery cannot replay a consumed identity. Consumption can safely skip a notification if the process stops between storing the receipt and posting.

Only future window starts are scheduled. Starting or resuming recording inside a window does not backfill a missed reminder. Inexact Android scheduling may delay delivery: over 60 seconds late, after window end, permission-blocked or ineligible recordings are consumed without posting. A shown notification expires at window end; process death can leave that already-posted notification until Android dismisses it or the timeout expires. Reopening/saving Travel, boot, package replacement and existing time/time-zone reconciliation rebuild future scheduling. Explicit manual flashlight arming and its stop/review protections remain unchanged.

## Data and portability

The private version-1 travelPlan JSON adds optional Boolean trackingReminders. Older records with the field absent read as false, without a migration write or default activation. Non-Boolean values are rejected while keeping the existing record. Explicit Save writes the field atomically with the trip and cue configuration, generating fresh revisions. Existing records, SQLite history/schema, daylight-reminder identities and light-cue runtime journals are unchanged. New private preference keys travelTrackingPending, travelTrackingConsumed, travelTrackingReminderError and travelTrackingLastNotice hold only reminder identity/status; no sensor data or credentials.

Portable settings profile version 1 deliberately includes only its existing five typed categories. Travel configuration, this opt-in, pending requests and consumed receipts are excluded from export/import. Record JSON backups likewise exclude application preferences. Importing a portable profile does not activate, disable or transfer this local travel setting; a fresh installation starts off. No cross-device schedule or active recording ownership is transferred.

## Verification boundary

Targeted source compilation establishes Java integration only. The focused existing Travel native method is extended separately with private preferences, fake clock, eligible/ineligible manual owner and an injected scheduler/notification port. It must establish draft/recreation/Save/reopen, consumption, duplicate/stale/lifecycle rejection and zero flashlight calls before native acceptance. No physical phone, real AlarmManager timing, OS notification delivery, sensor capture, torch output or clinical effect is claimed by source compilation.
